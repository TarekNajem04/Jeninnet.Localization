# Strongly Typed Keys

String keys are flexible and easy to pass around, which is exactly why they fail quietly. A typo
becomes a runtime miss; a rename leaves stale keys in half the call sites; a catalog change has no
compiler-visible effect. The key generator turns catalog keys into `const string` fields so those
failures become build errors.

This chapter covers the generator, the generated API, the localizability analyzer, and the
configuration that connects them to a project.

## Why compile-time keys

Generated keys make typos build errors, make renames produce solution-wide compile errors instead
of silent stale literals, and let the IDE list available keys. They also enable the localizability
analyzer's code fix: when a literal exactly matches a known constant, the analyzer can replace it.

## Setting up the generator

The generator package is a build-time analyzer. Reference it with private assets so it does not
become a runtime dependency:

```xml
<ItemGroup>
  <PackageReference Include="Jeninnet.Localization.Generators.Keys" Version="1.0.0" PrivateAssets="all" />
</ItemGroup>
```

Declare the catalogs as additional files. Only files whose names end in `.loc.json` are considered:

```xml
<ItemGroup>
  <AdditionalFiles Include="Localization\en.loc.json" />
  <AdditionalFiles Include="Localization\ar.loc.json" />
</ItemGroup>
```

If the same files are also served at runtime, copy them to the output directory and register them
with explicit paths:

```xml
<ItemGroup>
  <None Update="Localization\*.loc.json" CopyToOutputDirectory="PreserveNewest" />
</ItemGroup>
```

```csharp
var directory = Path.Combine(AppContext.BaseDirectory, "Localization");

services.AddJsonLocalizationProviders(builder => builder
    .AddCulture("en", Path.Combine(directory, "en.loc.json"))
    .AddCulture("ar", Path.Combine(directory, "ar.loc.json")));
```

The builder overload accepts explicit paths, so the generator's canonical files can also be the
runtime files. If you use the convention overload (`AddJsonLocalizationProviders(baseDirectory,
cultures)`), it expects `{culture}.json`, not `{culture}.loc.json`; do not put `.loc.json` files in
a directory that is auto-discovered as culture files.

## Input contract

Each `*.loc.json` file is a flat JSON object mapping string keys to string templates. The generator
rejects anything outside that shape as a build error:

- malformed JSON or a non-object root;
- non-string keys or values;
- duplicate keys in one file;
- two keys that sanitize to the same identifier, or a key with no identifier characters;
- an invalid configured namespace.

Templates stay in the provider. The generator emits keys only, never message text.

## Generated API shape

For a catalog containing `App.Title` and `Cart.Items`, the generator emits a compilation unit
equivalent to:

```csharp
// <auto-generated/>
#nullable enable
namespace MyApp.Generated;

public static partial class LocalizationKeys {
    public const string APP_TITLE = "App.Title";
    public const string CART_ITEMS = "Cart.Items";
    public static readonly string[] All = new string[] { "App.Title", "Cart.Items" };
}
```

The class is always `public static partial class LocalizationKeys`, with one `const string` per key
and a keys-only `All` array. Identifiers are upper snake case; separators and camel/acronym
boundaries split words (`BookId` to `BOOK_ID`, `OrderID` to `ORDER_ID`), and a leading digit gains
an underscore. Constants and `All` are ordinal-sorted; output is deterministic and byte-identical
for fixed input. Multiple catalogs contribute to one class. The `partial` modifier allows helpers,
but generated constants should never be edited.

## Namespace configuration

Without configuration, the namespace is `{AssemblyName}.Generated`. Override it with an MSBuild
property and make that property visible to the compiler:

```xml
<PropertyGroup>
  <LocalizationKeysNamespace>MyApp.Localization</LocalizationKeysNamespace>
</PropertyGroup>
<ItemGroup>
  <CompilerVisibleProperty Include="LocalizationKeysNamespace" />
</ItemGroup>
```

The `CompilerVisibleProperty` item is required; without it the generator silently falls back to
`{AssemblyName}.Generated`. The build succeeds, so the wrong namespace is easy to miss.

## Build-time diagnostics

Every generator failure is a build **error** with a file and line where the content supplies one.
Malformed content never produces a silent skip or a partial class.

| Diagnostic | Meaning |
|---|---|
| `JLNKEY001` | The catalog is not well-formed JSON, or the root is not a JSON object. |
| `JLNKEY002` | An entry does not map a string key to a string template. |
| `JLNKEY003` | The same key occurs more than once in one catalog file. |
| `JLNKEY004` | Two distinct keys sanitize to the same C# identifier. |
| `JLNKEY005` | A key contains no identifier characters. |
| `JLNKEY006` | The configured namespace is not a legal dotted C# identifier. |

Treat these as catalog validation. A red build means the canonical key set is ambiguous or
malformed, which is preferable to discovering it at runtime.

## Using the keys

```csharp
var text = await localizer.LocalizeAsync(
    LocalizationKeys.CART_ITEMS,
    new Dictionary<string, object?> { ["count"] = count },
    CultureInfo.CurrentUICulture);
```

The constants are ordinary strings and work with `LocalizeWithContextAsync` and
`LocalizePluralAsync`, but the generator does not encode context or plural pairing. For a plural
pair, define both keys and pass the two constants.

## The localizability analyzer

The `Jeninnet.Localization.Analyzers.Localizability` package flags hardcoded user-facing strings so
authors move them into the pipeline at authoring time. Its single diagnostic is `JLNLOC001`.

Flagged shapes include UI text assignments (`control.Text`, `Title`, `Header`, `Content`,
`Caption`, `ToolTip`, `PlaceholderText`), `ViewData`/`ViewBag` entries, `MessageBox.Show`,
exception messages, validation messages (`AddModelError`, `ErrorMessage`, `Display(Name)`), and API
problem messages. Identifiers, logging, test assertions, local initializers, empty strings, and
non-key compositions are quiet by design.

The default severity is hidden (the editor suggestion level). Opt into warnings or errors with
`LocalizabilitySeverity` (`suggestion`, `warning`, `error`) declared visible via
`<CompilerVisibleProperty Include="LocalizabilitySeverity" />`, or with
`dotnet_diagnostic.JLNLOC001.severity = warning` in `.editorconfig`. `.editorconfig` wins on
conflict. Standard suppression works: `#pragma`, `[SuppressMessage]`, or a per-folder section.

### The code fix

When the flagged literal exactly equals a `const string` in a `*Keys` class — hand-written or
generated — the code fix replaces the literal with a fully qualified reference to that constant.
Literals with no matching constant get no fix. The analyzer does not extract strings into catalogs;
that is an explicit authoring decision, and the parity tool reports gaps rather than writing them.

**Pitfall:** a code fix is not a translation workflow. Replacing a literal with a constant makes the
call site type-safe, but the key still needs a catalog entry for every served culture. Run the
parity tool after applying fixes.

## Worked example: from catalog to call site

1. Create `Localization/en.loc.json` with `App.Title` and `Cart.Items`.
2. Add it as an `AdditionalFile`, set `LocalizationKeysNamespace`, and add the matching
   `CompilerVisibleProperty`.
3. Build. The class contains `APP_TITLE` and `CART_ITEMS`.
4. Register the same file with the JSON provider using the explicit builder overload.
5. Use `LocalizationKeys.CART_ITEMS` at the call site.
6. Add the Arabic catalog. The generator produces the union of keys; the parity tool reports
   missing translations.

Generated keys follow every declared catalog, not the translations: a key present only in
`ar.loc.json` still generates a constant.

## Build-time behavior and packaging

The generator ships as an analyzer asset under `analyzers/dotnet/cs` with
`DevelopmentDependency=true`, targets `netstandard2.0` for every Roslyn host, and never becomes a
runtime dependency. Generation is incremental: unchanged catalogs reuse cached parse results, and
one emit step produces the class. The analyzer package uses the same packaging model.

## Pitfalls

**Pitfall:** adding a catalog as `Content` instead of `AdditionalFiles`. The file is copied or
served but the generator never sees it, so no constants are produced. There is no error; the class
is simply absent or stale.

**Pitfall:** forgetting `CompilerVisibleProperty` for the namespace. The build succeeds and the
constants land in `{AssemblyName}.Generated`, which may not be the namespace you expect.

**Pitfall:** expecting the generator to validate translations. It validates the key catalogs it
reads. Missing cultures, placeholder drift, and unused keys are parity-tool findings, not
generator diagnostics.

**Pitfall:** putting `.loc.json` files in an auto-discovered runtime directory. The JSON convention
overload treats every `*.json` file stem as a culture code, so `en.loc.json` is not culture `en`.
Use explicit builder paths or keep generator inputs separate from runtime catalogs.

**Pitfall:** treating a green build as localization coverage. Compile-time keys prove the key
exists in a declared catalog, not that it exists in every language. Use
[Parity and quality gates](13-parity-and-quality-gates.md).
