# دليل أداء (performance evidence)

هذه الصفحة لقطة أدلة قابلة لإعادة الإنتاج للمسارات الساخنة الموثّقة. إنها ليست مجموعة قياس، ولا
وعد سعة، ولا SLO. تؤكد اختبارات الأداء في المستودع فقط أن القياسات موجبة ومنتهية؛ والأرقام أدناه
هي الوسيطات من تشغيلين متتاليين على جهاز واحد، تُنشر كي يرى القارئ شكل الكلف ويعيد إنتاجها.

للشرح البنيوي لخط الأنابيب وكلف المزوّدين، اقرأ [الأداء](03-performance.md) أولاً. تضيف هذه الصفحة
قياسات، لا سلوكاً جديداً.

## البيئة والطريقة

| البند | القيمة |
|---|---|
| تاريخ التشغيل | 2026-10-21 |
| وقت التشغيل | .NET 10.0.13 |
| نظام التشغيل | Microsoft Windows 10.0.26300 |
| معمارية العملية / نظام التشغيل | X64 / X64 |
| المعالجات المنطقية | 12 |
| Server GC | معطّل |
| دقة Stopwatch | عالية الدقة، 10,000,000 Hz |
| الثقافة أثناء التشغيل | <code dir="ltr">en-NL</code> (التنسيق)، <code dir="ltr">en-US</code> (الواجهة) |
| التكوين | Release، بلا بناء |
| مرشح الاختبار | <code dir="ltr">TestCategory=Performance</code> |
| الكتل / العينات | 7 كتل موقوتة للحالة المستقرة؛ و5 للتحميل الأول وSQLite والتشخيص |

يسخّن المِحمل كل سيناريو، ويسجّل الزمن المنقضي بـ
<code dir="ltr">Stopwatch.GetTimestamp()</code>، ويسجّل التخصيصات بـ
<code dir="ltr">GC.GetAllocatedBytesForCurrentThread()</code>. وتبلّغ كل نتيجة عن الأدنى والوسيط
والأقصى عبر الكتل؛ وتستخدم الجداول أدناه الوسيط. والتخصيص هو وسيط البايتات لكل عملية.

أعد الإنتاج من جذر المستودع:

<div dir="ltr">

```powershell
dotnet build tests/Jeninnet.Localization.Tests/Jeninnet.Localization.Tests.csproj -c Release
dotnet test tests/Jeninnet.Localization.Tests/Jeninnet.Localization.Tests.csproj `
    -c Release --no-build `
    --filter "TestCategory=Performance" `
    --logger "console;verbosity=detailed"
```

</div>

تُكتب أسطر <code dir="ltr">RESULT</code> و<code dir="ltr">ENV</code> و
<code dir="ltr">NOTE</code> عبر سياق الاختبار. شغّل الأمر مرتين وقارن الوسيطات؛ لا تقارن بجهاز آخر
أو بتشغيل جرى والجهاز مشغول.

| السيناريو | وسيط التشغيل A | وسيط التشغيل B | وسيط التخصيص (A / B) |
|---|---:|---:|---:|

| <code dir="ltr">IMessageLocalizer</code>، موجود دقيق، 1,000 مفتاح | 557.2 ns | 662.4 ns | 88 / 88 B |
| <code dir="ltr">IMessageLocalizer</code>، مفتاح مفقود، 1,000 مفتاح | 455.7 ns | 313.5 ns | 208 / 208 B |
| <code dir="ltr">IMessageLocalizer</code>، <code dir="ltr">fr-FR</code> يرتد إلى <code dir="ltr">en</code>، 1,000 مفتاح | 278.6 ns | 181.5 ns | 88 / 88 B |
| مزوّد ResX، بحث دقيق متكرر | 115.8 ns | 197.3 ns | 0 / 0 B |
| جسر المخزن، <code dir="ltr">IStringLocalizerFactory.Create</code> | 57.4 ns | 48.3 ns | 40 / 40 B |
| جسر المخزن، بحث مفهرس <code dir="ltr">IStringLocalizer</code> | 234.4 ns | 251.4 ns | 144 / 144 B |
| مزوّد SQLite، قاعدة بيانات في الذاكرة، اتصال + استعلام لكل نداء | 90.2 ميكروثانية | 114.0 ميكروثانية | 2,576 / 2,576 B |
| التشخيص غائب، بلا مستمعين | 138.1 ns | 170.1 ns | 88 / 88 B |
| التشخيص مُراقَب، مستمع نشاط ومقياس يسجّلان | 5.76 ميكروثانية | 8.85 ميكروثانية | 1,849 / 1,849 B |

استخدم تشغيل التشخيص 5,000 عملية لكل كتلة، و5 كتل، و1,000 مفتاح. وسجّل التشغيل المراقَب 51,000
نشاط و76,500 قياس في كل تمريرة. وكانت نسبة وسيط المراقَب/الغائب 41.70 في التشغيل A و52.02 في
التشغيل B؛ فالمستمعون يدفعون كلف التسجيل، والمضيف بلا مستمعين يدفع فحوص حماية المستمع فقط.

## مزوّدات الملفات

يقيس التحميل الأول إنشاء المزوّد وتحليل/تحميل الملف وبحثاً دقيقاً واحداً. وتقيس الحالة المستقرة
عمليات بحث دقيقة متكررة بعد تحميل الجدول. ويستخدم JSON وXML تجهيزات المفاتيح/القوالب نفسها.

| السيناريو | وسيط التشغيل A | وسيط التشغيل B | وسيط التخصيص (A / B) |
|---|---:|---:|---:|
| تحميل JSON الأول، 10 مفاتيح | 130.2 ميكروثانية | 185.3 ميكروثانية | 4,152 / 4,152 B |
| تحميل XML الأول، 10 مفاتيح | 276.2 ميكروثانية | 187.6 ميكروثانية | 11,424 / 11,424 B |
| تحميل JSON الأول، 1,000 مفتاح | 795.6 ميكروثانية | 764.0 ميكروثانية | 333,664 / 333,664 B |
| تحميل XML الأول، 1,000 مفتاح | 1.348 ms | 1.640 ms | 482,336 / 482,336 B |
| تحميل JSON الأول، 10,000 مفتاح | 6.904 ms | 8.339 ms | 3,327,312 / 3,327,312 B |
| تحميل XML الأول، 10,000 مفتاح | 22.892 ms | 26.948 ms | 4,658,064 / 4,657,864 B |
| حالة JSON المستقرة، 1,000 مفتاح | 51.1 ns | 64.4 ns | 0 / 0 B |
| حالة XML المستقرة، 1,000 مفتاح | 54.1 ns | 62.4 ns | 0 / 0 B |
| حالة JSON المستقرة، 10,000 مفتاح | 46.5 ns | 56.2 ns | 0 / 0 B |
| حالة XML المستقرة، 10,000 مفتاح | 45.2 ns | 56.2 ns | 0 / 0 B |

وسيطات الحالة المستقرة عمليات بحث قاموس ولا تمس نظام الملفات. ويتوسع التحميل الأول مع حجم الملف؛
ويحلّل XML أبطأ ويخصص أكثر من JSON للتجهيزة نفسها. والتحميل الفاشل لا يُخزَّن، فيدفع الملف المعطوب
كلفة الفشل ثانيةً في المحاولة التالية.

## ماذا تعني الأرقام

- **عمليات البحث داخل العملية عشرات النانوثانية.** عمليات بحث الذاكرة وJSON/XML المحمَّل في الحالة
  المستقرة من الرتبة نفسها. ويُهيمن شكل جدول المزوّد وتوزيع المفاتيح.
- **Core يضيف التنسيق والارتداد، لا الإدخال/الإخراج.** مسارات الإصابة والغياب والارتداد مئات
  النانوثانية وعشرات إلى مئات البايتات لكل عملية. ومزوّد قاعدة بيانات أو ترجمة أغلى بآلاف المرات
  من هذه الطبقة.
- **التحميل الأول كلفة مسار بارد.** تحليل JSON/XML عند 10,000 مفتاح يُقاس بالمللي ثانية وبميغابايتات
  من التخصيص؛ فدفّئ الكتالوج قبل بداية حساسة للزمن إذا كانت البداية الباردة مهمة.
- **SQLite في الذاكرة مسار قاعدة بيانات رغم ذلك.** اتصال واستعلام لكل نداء يكلفان نحو 90–114 ميكروثانية
  لكل بحث في هذه التشغيلات، حتى مع قاعدة بيانات في الذاكرة. وقاعدة البيانات الشبكية تضيف زمن شبكة
  فوق ذلك. خزّن مؤقتاً فوق المزوّد أو قلّل خطوات الارتداد.
- **التشخيص يدفعه المراقب.** بلا مستمعين، تكون الكلفة في نطاق أقل من ميكروثانية. ومع مستمعي نشاط
  ومقياس يسجّلان، ترتفع الكلفة نحو 40–50× في هذا الحمل. هذا تصميم حماية المستمع المقصود، لا سبب
  لتجنب الأدوات في الإنتاج؛ خصص له ميزانية عند تفعيل تسجيل عالي التعددية.
- **جسر المخزن رخيص الإنشاء والقراءة.** إنشاء مُعرِّب والقراءة عبر جسر المخزن عمليتان أقل من
  ميكروثانية على المخزن داخل العملية المقاس. والمخزن المسنود بقاعدة بيانات يدفع كلفة استعلامه.

## تحفظات

- هذه **تشغيلتان على جهاز واحد**، لا توزيع. وكان التشغيل الثاني أكثر ضجيجاً في عدة سيناريوهات (مثلاً
  <code dir="ltr">IMessageLocalizer</code> الدقيق 557 → 662 ns وSQLite 90 → 114 ميكروثانية). استخدم
  الوسيطات كشكل رتبة مقدار، لا كضمان.
- يبلّغ المِحمل عن الأدنى/الوسيط/الأقصى عبر الكتل، لا p95/p99. وللتخطيط الحساس للذيل، قس مسار
  إنتاجك وسجّل المئينات.
- كان Server GC معطّلاً وللجهاز 12 معالجاً منطقياً. أجهزة أو حالة طاقة أو وضع GC أو حمل خلفي أو
  إصدار تصحيح وقت تشغيل مختلف تغيّر الأرقام.
- قياس SQLite يستخدم قاعدة بيانات في الذاكرة واتصالاً لكل نداء. وهو لا يقيس إدخال/إخراج الملفات
  أو إعدادات WAL أو قواعد البيانات الشبكية أو تدفئة مجمع الاتصالات.
- قياسات الملفات تستخدم تجهيزات مولّدة صغيرة، لا كتالوجك. وطول القالب وطول المفتاح والترميز وعدد
  الثقافات كلها تؤثر في زمن التحليل والتخصيص.
- الاختبارات غير بوابية. تؤكد قياسات موجبة منتهية، لا عتبات؛ وتشغيل اختبار أخضر ليس ميزانية أداء.

## إعادة إنتاج تغيير وتفسيره

1. شغّل الأمر أعلاه على جهاز هادئ ببناء Release.
2. التقط أسطر <code dir="ltr">ENV</code> و<code dir="ltr">RESULT</code> و
   <code dir="ltr">NOTE</code> في ملف.
3. شغّله ثانية وقارن الوسيطات سيناريو بسيناريو، لا أسرع صف فقط.
4. غيّر شيئاً واحداً (المزوّد، حجم الكتالوج، الذاكرة، المستمع) وأعد.
5. فضّل الشرح البنيوي في [الأداء](03-performance.md) عندما يتحرك رقم؛ فالقياس يفسّر الكلفة، لا
   السبب.

إشارات وقت التشغيل المفيدة للإنتاج معرّفة بالفعل:
<code dir="ltr">localization.lookup.duration</code> و
<code dir="ltr">localization.lookup.hits</code> و
<code dir="ltr">localization.lookup.misses</code> و
<code dir="ltr">localization.fallback.steps</code> وأدوات طلب/ذاكرة/مدة الترجمة تحت مقياس
<code dir="ltr">Jeninnet.Localization</code>. وهي محمية بمستمع أيضاً.
